# Phase 0 - Project Foundation (Learning Notes)

This document explains the tools and concepts introduced in Phase 0, written
for a developer who is comfortable with C++ but new to CMake, CTest, Ninja and
GoogleTest. Everything below was actually executed on this machine; the exact
commands and results are recorded at the end.

---

## 1. What is CMake?

CMake is a **build system generator**. You write a plain-text description of
your project - what source files exist, what executables/libraries they form,
and what flags/options to use - in files named `CMakeLists.txt`. CMake then
generates the actual build files for the tool you want to use (Ninja, "Unix
Makefiles", Visual Studio solutions, and so on).

It is not a compiler and it is not a build tool itself. It is the layer in
between: one project description, many supported build backends and
platforms.

## 2. Why CMake instead of manually invoking g++?

You *can* build this project by hand:

```bash
g++ -std=c++20 -Wall -Wextra -Wpedantic src/main.cpp -o app.exe
```

That works for one file, but it does not scale:

- A real project has many files; compiling them all every time wastes time
  and there is no incremental rebuild.
- Dependencies (like GoogleTest) have to be downloaded, configured and
  compiled manually.
- Flags, include paths and settings are scattered and easy to forget.
- The recipe is not portable to another compiler or another operating system.

CMake centralises all of this in one place. You declare what you want, and
CMake (together with the build tool) figures out what to compile, in what
order, and what needs recompiling after a change. It also gives us `CTest`
for running tests and `FetchContent` for pulling in dependencies.

## 3. What is a CMake target?

A **target** is CMake's name for a buildable unit - typically an executable
or a library. Each target has:

- a name (used to refer to it from other targets and the command line);
- source files;
- compile options and definitions;
- include directories;
- link dependencies on other targets.

In this project there are two first-party targets:

- `DistributedSearchEngine` - the application executable;
- `smoke_test` - the test executable.

`add_executable(name src1.cpp src2.cpp ...)` creates an executable target;
`add_library(name STATIC ...)` would create a library target.

## 4. Executable vs library targets

- An **executable** target produces a program that can be run directly (it
  has a `main` function). Example: `DistributedSearchEngine`.
- A **library** target produces compiled code that is *linked into* something
  else; it has no `main` and cannot run by itself. Libraries exist to share
  code (e.g. the search engine core) between multiple executables, such as
  the application and its test suite.

Phase 0 deliberately has **no library yet**: the instruction for this phase
is to keep the structure minimal. In Phase 1, when real components such as
tokenizers appear, we will introduce a library so that the same code can be
linked into both the application and the unit tests.

## 5. What is Ninja?

Ninja is a **build tool** (the thing that actually runs the compiler and
linker). It is designed to be extremely fast at incremental builds: it knows,
from the files generated by CMake, exactly which commands to run and in which
order, and it only recompiles what actually changed.

Compared to `make`, Ninja does less itself - it deliberately has almost no
language for describing builds - and instead consumes a `build.ninja` file
that CMake generates for it. That split is why the two tools work so well
together.

## 6. How CMake generates Ninja build files

When you run:

```bash
cmake -S . -B build -G Ninja
```

CMake reads the root `CMakeLists.txt`, works out the target graph and the
exact compiler/linker commands needed, and writes them into the `build/`
directory, including a `build.ninja` file. `cmake --build build` then invokes
Ninja on that file. The generator flag (`-G Ninja`) is what picks Ninja as
the backend; without it CMake would use its default generator for the
platform.

## 7. What "C++20" means in this project

C++20 is the language standard this project targets. The three relevant CMake
variables:

- `CMAKE_CXX_STANDARD 20` - ask the compiler for C++20;
- `CMAKE_CXX_STANDARD_REQUIRED ON` - fail the build if the compiler cannot
  provide C++20 instead of silently falling back;
- `CMAKE_CXX_EXTENSIONS OFF` - use strict standard C++20 (`-std=c++20`)
  rather than the compiler's GNU extensions (`-std=gnu++20`).

The smoke test already uses a C++20-era feature (`std::string_view`, which
arrived in C++17 and is fully supported in C++20), and the executable prints
`__cplusplus` so you can see the standard it was built with (`202002L`).

## 8. What is GoogleTest?

GoogleTest (gtest) is a C++ unit-testing framework. You write tests as
functions registered with the `TEST(SuiteName, TestName)` macro; the
framework runs them, reports pass/fail per test, and provides rich assertion
macros. The sibling project GoogleMock (gmock) adds mocking support; Phase 0
disables it (`BUILD_GMOCK OFF`) because we do not need it yet.

GoogleTest is brought into the build with `FetchContent`, which downloads it
from GitHub at configure time and compiles it as part of our build. It is
**pinned to the `v1.18.0` release tag** so that every configure uses exactly
the same code - see section 12.

## 9. EXPECT_* vs ASSERT_*

Both families perform a check and record a failure, but they differ in what
happens after a failure **within the same test**:

- `EXPECT_EQ(a, b)` (and `EXPECT_TRUE`, `EXPECT_FALSE`, ...) - non-fatal: the
  check fails, but the rest of the test function continues to run.
- `ASSERT_EQ(a, b)` (and `ASSERT_TRUE`, ...) - fatal: the check fails and the
  test function aborts immediately.

Rule of thumb: use `ASSERT_*` when the code after the check cannot safely run
if the assertion failed (e.g. dereferencing a pointer that should not be
null), and `EXPECT_*` when you want to report as many failures as possible in
one run. The smoke test demonstrates both: `ASSERT_EQ` on the string content
(if that failed, the size check would be meaningless), and `EXPECT_EQ` for
independent checks.

## 10. What is CTest?

CTest is CMake's **test runner**. It does not know about GoogleTest
specifically; it runs any registered test and reports results. The CMake
command `gtest_discover_tests(smoke_test)` registers every `TEST(...)` case
from the `smoke_test` executable with CTest automatically.

You run all tests with:

```bash
ctest --test-dir build --output-on-failure
```

This is the command used in CI-style checks: it exits non-zero if any test
fails, and `--output-on-failure` prints the failing output to help debugging.

## 11. Debug vs Release builds

The compiler can optimise the code and/or add debugging information:

- **Debug** - no (or little) optimisation, full debug symbols: easier to
  step through in a debugger, but slower binaries. Good for development.
- **Release** - optimised (`-O2`/`-O3`), minimal debug info: faster binaries,
  harder to debug. Good for benchmarking and deployment.

With the Ninja generator the build type is set at configure time, e.g.
`-DCMAKE_BUILD_TYPE=Debug` (default) or `-DCMAKE_BUILD_TYPE=Release`. With
multi-config generators (like Visual Studio) you instead pass `--config`
at build time. Phase 0 uses the default (Debug); benchmarking in later phases
will require Release builds.

## 12. Why dependencies should be pinned

`FetchContent_Declare(... GIT_TAG v1.18.0 ...)` pins GoogleTest to a specific
release. If instead we tracked a moving branch (e.g. `main`), every fresh
configure could silently pull a different version of the dependency. That
breaks **reproducibility**:

- a project that builds today might not build next week;
- tests might pass today and fail tomorrow for reasons unrelated to our code;
- two developers would be testing against different versions.

Pinning to a release tag means the same code is fetched every time, which is
a prerequisite for trustworthy results (including the benchmark numbers
required in later phases).

## 13. Why the UCRT64 toolchain instead of the old GCC 8.1

This machine has two GCC installations. The relevant one is the **MSYS2
UCRT64** toolchain:

- `C:\msys64\ucrt64\bin\g++.exe` - **GCC 16.2.0**;
- `C:\msys64\ucrt64\bin\cmake.exe` - **CMake 4.4.2**;
- `C:\msys64\ucrt64\bin\ninja.exe` - **Ninja 1.13.2**.

The other one (CodeBlocks MinGW, **GCC 8.1.0**) is on the `PATH` by default
and must not be used, because:

- C++20 support is essentially absent in GCC 8 (concepts, ranges, `<=>`,
  `std::span` and friends landed in GCC 10+); the project requires C++20;
- it is from 2018, unmaintained, and paired with an old MinGW runtime;
- using it would produce confusing failures that have nothing to do with our
  code.

MSYS2 UCRT64 is a modern, actively maintained environment whose packages
(GCC, CMake, Ninja) are kept consistent with each other, and its UCRT runtime
is the modern Microsoft Universal C Runtime. Before invoking CMake we put the
UCRT64 `bin` directory first on `PATH` so that `cmake`, `ninja`, `g++` and
the runtime DLLs used by compiled programs are all resolved from there.

## Commands actually used

```bash
# 1. Make the UCRT64 toolchain the one that is found first.
export PATH="/c/msys64/ucrt64/bin:$PATH"

# 2. Configure: read CMakeLists.txt, download GoogleTest, generate Ninja files.
cmake -S . -B build -G Ninja \
  -DCMAKE_CXX_COMPILER=/c/msys64/ucrt64/bin/g++.exe \
  -DCMAKE_MAKE_PROGRAM=/c/msys64/ucrt64/bin/ninja.exe

# 3. Build the application and the test executable.
cmake --build build

# 4. Run the test suite through CTest.
ctest --test-dir build --output-on-failure

# 5. Run the application itself.
./build/DistributedSearchEngine.exe
```

Expected output of step 4: both smoke tests pass (2/2 tests, 0 failures).
Expected output of step 5: the application prints its name, phase, and
`Built with C++ standard: 202002L`.
